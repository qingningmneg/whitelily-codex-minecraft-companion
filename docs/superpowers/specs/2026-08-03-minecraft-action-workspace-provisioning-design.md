# WhiteLily Minecraft 动作工作区子程序设计

日期：2026-08-03
状态：已由用户确认

## 背景与已确认根因

真实安装版中，模型会回答“无法调用动作”。诊断证据表明：

- 每一个真实任务审计记录的 `toolCalls` 都是 `0`。
- Codex 会话的工作目录为 `%LOCALAPPDATA%\WhiteLily\codex-workspace`。
- 该目录在安装环境中不存在。
- 安装资源也没有包含 `codex-workspace/AGENTS.md` 和 `.codex/config.toml`。
- Electron `extraResources` 只打包 core、Codex、licenses 和 runtime manifest。

源代码本来依赖工作区中的 MCP 配置把 `http://127.0.0.1:32123/mcp` 注册为 `minecraft` 服务器。工作区缺失后，模型看不到任何 `minecraft_` 工具，所以问题发生在工具发现之前，而不是动作执行器内部。

## 目标

1. 安装版始终拥有受版本管理的专用 Codex 工作区。
2. AI 会话创建前验证 Minecraft MCP 服务器和完整工具目录。
3. 工具未准备好时禁止启动可执行任务，避免模型用文字声称无法调用。
4. 工作区部署、升级和修复必须原子化、可诊断且不接触用户游戏存档。
5. 动作子程序作为独立启动边界运行，不和模型热切换逻辑耦合。

## 非目标

- 本次不新增 Minecraft 动作类型。
- 本次不放宽现有安全预算、方块修改限制、危险动作确认或主人身份检查。
- 本次不把 Minecraft 存档、认证数据或原始聊天写入诊断包。
- 本次不允许模型调用 shell、文件编辑或非 `minecraft_` 工具。

## 架构

### 1. 版本化工作区资源

Electron 构建产物增加只读资源目录 `resources/codex-workspace`，只包含：

- `AGENTS.md`：限制游戏会话只能使用 `minecraft_` 工具，并要求中文、简短、玩家可见的回复。
- `.codex/config.toml`：注册固定回环地址 `http://127.0.0.1:32123/mcp`。
- `workspace-manifest.json`：记录 schema version、内容版本以及 `AGENTS.md` 和 `.codex/config.toml` 的 SHA-256。该清单自身由外层 runtime manifest 校验，避免自哈希循环。

构建与 after-pack 检查必须拒绝缺文件、多余文件、路径逃逸、非回环 MCP 地址或哈希不一致的安装包。

### 2. WorkspaceProvisioner 子程序

主进程在启动 WhiteLily 子进程之前运行 `WorkspaceProvisioner`：

1. 验证打包资源清单和哈希。
2. 在数据根目录内创建唯一临时目录。
3. 把受管文件复制到临时目录并重新计算哈希。
4. 将旧工作区移动为同根备份，再把临时目录原子替换为 `%LOCALAPPDATA%\WhiteLily\codex-workspace`。
5. 验证成功后删除旧备份；失败则恢复旧目录并终止子进程启动。

工作区是应用受管资源，不存放记忆、配置档案、日志、认证数据或用户内容，因此升级可以完整替换。所有解析路径必须被验证为位于 WhiteLily 数据根目录或只读安装资源根目录内。

### 3. 动作服务器就绪门

运行时保持既有顺序，但增加可验证门槛：

1. 连接 Mineflayer 并建立安全上下文。
2. 启动回环地址上的 Minecraft MCP 服务器。
3. 使用独立 MCP 客户端连接 `/mcp` 并调用 `tools/list`。
4. 将实际工具名与代码定义的精确允许列表比较。
5. 只有工具列表完整、无额外非 `minecraft_` 工具时，才创建 Codex 线程并接受任务。

健康检查只读取工具元数据，不执行游戏动作。检查客户端随后关闭，模型线程使用同一固定 MCP 地址自行发现工具。

### 4. 运行时健康状态

运行时增加内部动作能力状态：`starting`、`ready`、`failed`。只有 `ready` 可以把玩家输入路由为可执行任务。

伙伴聊天线程和任务线程都必须等待动作能力进入 `ready` 才能创建。若验证失败，整个伙伴 AI 保持未启动，由 UI 显示稳定的本地错误；玩家输入不会交给模型猜测是否需要动作。诊断页显示脱敏错误代码、工作区版本、MCP 监听状态和已发现工具数量。

### 5. 与模型热切换的边界

WorkspaceProvisioner 只在应用/子进程启动前部署资源；模型热切换不重新复制工作区，也不重启 MCP 服务器。

模型切换创建新线程前复用动作服务器就绪门的当前健康快照。若动作能力失效，禁止新任务线程接管，但 Minecraft 连接仍由运行时按安全策略处置。

## 失败处理

- 安装资源缺失或哈希错误：阻止子进程启动，输出固定的工作区安装损坏错误。
- 临时部署失败：恢复旧工作区；旧工作区也无效时保持停止状态。
- 32123 端口占用：MCP 启动失败，不创建 Codex 任务线程。
- `tools/list` 超时、缺少工具或包含非法工具：标记动作能力失败并记录脱敏差异计数。
- Codex 线程创建后 MCP 后续断开：停止当前任务并撤销工具租约；不得让模型继续假装执行动作。
- 修复或重启后健康检查通过：重新允许任务，无需重新安装 Minecraft 或 PCL2。

## 测试设计

### 构建与安装包测试

- Electron bundle 和最终 unpacked 安装目录包含三个工作区资源。
- workspace manifest 覆盖两个工作区载荷文件，外层 runtime manifest 覆盖 workspace manifest，所有哈希一致。
- 路径逃逸、远程 MCP URL、额外文件和缺失文件均使打包失败。

### WorkspaceProvisioner 测试

- 首次启动从空目录部署完整工作区。
- 相同版本启动幂等且不产生残留临时目录。
- 旧版本升级为新版本。
- 复制、校验或原子替换失败时恢复旧版本。
- 不读取或修改 WhiteLily 数据根之外的文件。

### MCP 与运行时集成测试

- 实际 `/mcp` 的 `tools/list` 包含完整允许列表。
- 缺失一个工具、加入一个非 `minecraft_` 工具、端口冲突和超时均阻止任务线程启动。
- 健康检查不增加工具调用预算，也不执行 Mineflayer 动作。
- MCP 在任务中断开时，任务停止且审计记录终止原因。

### 真实安装版冒烟测试

1. 清洁安装或升级 WhiteLily。
2. 确认用户数据根出现受管 `codex-workspace`。
3. 启动 Minecraft 1.21.5 LAN 世界并连接 WhiteLily。
4. 对白百合说“查看一下你现在的位置”，确认审计 `toolCalls >= 1`。
5. 说“走到我身边来”，确认实际移动并记录对应安全预算。
6. 重启应用后重复工具发现与安全动作测试。

## 完成标准

- 最终安装包可以在空白用户数据目录上自动部署有效工作区。
- Codex 会话开始前已通过真实 MCP `tools/list` 健康检查。
- 安全动作请求产生真实 `minecraft_` 工具调用，审计计数不再恒为 0。
- 工具不可用时任务不会进入模型执行阶段。
- 构建、集成、安装生命周期与真实世界冒烟测试全部通过。
